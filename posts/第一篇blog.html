第一篇blog

2026-11-03·#折腾 #随笔

我一直在等一个"合适的时候"再开博客。

等有空、等想清楚要写什么、等先把博客系统搭好。这三件事互相等待，于是什么都没发生。后来我想明白了，问题不在顺序——是我把"搭博客"当成了一个需要郑重对待的工程。

所以这次反过来：先不管搭得好不好，先让它存在。

一台手机就够

真正的约束是，我大部分时间只有一台手机。

开电脑写一篇东西，成本太高。不是没时间，是"要用电脑"这个前提本身就会让人放弃。而手机一直在手上，地铁上、睡前、等外卖的时候，想法来了就能记下来。

于是我给自己定了三条：能离线写、存在本地、一键发出去。

它就是一个 html 文件

没有 App，没有安装包，没有服务器。

一个 69KB 的 html 文件，丢在手机存储里，用浏览器打开。它既是编辑器，也是静态站点生成器。

写完点发布，它把整站重新生成一遍——首页、每篇文章、标签页、归档、RSS、sitemap——然后通过 GitHub 的接口一次性提交进仓库。GitHub Pages 直接吐出文件，中间不需要任何构建步骤。

这个设计有个好处：你在手机上看到的样子，和网上看到的样子，是同一份代码画出来的。不存在"本地预览正常、上线就歪了"这种事。

三个坑

第一个：空仓库没有分支。

新仓库如果没勾 README，它是彻底空的，连 main 分支都没有。

我的代码本来设想好了这条路：读不到分支就自己建一个。结果第一次发布就报 409。

我以为是权限问题，折腾了半天。后来才知道，GitHub 对空仓库读分支返回的是 409 Git Repository is empty，不是我以为的 404 Not Found。代码只处理了 404，409 被当成普通异常直接抛了出去，建分支那段逻辑一次都没跑到。

修法很土：读不到分支时，先用接口写一个 README 把分支顶上，再走正常流程。

第二个：Token 只读。

这个更蠢。建 token 的时候，权限那一栏我给了 Contents 的 Read-only。

但发布是要写。于是初始化那步顺利通过，上传文件时 403。

GitHub 的原文是 Resource not accessible by personal access token，翻译过来就是"这个 token 够不着"。改成 Read and write，权限立刻生效，不用重新生成。

第三个：浏览器会藏东西。

这个不算 bug，是设计。

本地 html 用 file:// 打开时，Chrome 直接禁用 IndexedDB，只能用 localStorage，大概 5MB。

更麻烦的是，每个 file:// 路径是独立的存储空间。你把 html 挪个目录、改个文件名，之前写的东西就读不到了——不是丢了，是新身份看不到旧数据。

所以这个编辑器里必须有个导出按钮。我现在隔几天导一次 JSON，丢网盘。

现在

能用了。

写、存、发，三步。发布通常几秒钟，只会上传改动过的文件。

它肯定还会坏。浏览器的存储策略会变，GitHub 的接口会变，我换手机的时候数据还得手动搬。

但那些都是"以后"的事。现在有一件事已经解决：想法来的时候，我不用等电脑了。

至于以后写什么——还没想好。可能就写这种：做东西的时候卡在哪儿，怎么绕过去的。
